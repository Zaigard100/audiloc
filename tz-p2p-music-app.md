# ТЗ: кроссплатформенный P2P музыкальный плеер с автосинхронизацией библиотеки

## 1. Цель проекта

Приложение для Linux, Windows и Android, которое хранит музыкальную библиотеку локально на каждом устройстве и автоматически синхронизирует файлы, жанры, альбомы и избранное между устройствами при появлении в одной сети — без облака и без центрального сервера. Интерфейс — в стилистике Яндекс Музыки (тёмная тема, мини-плеер снизу, вкладки библиотеки, крупные обложки), но без копирования логотипа и брендированных элементов.

## 2. Ключевое архитектурное решение

Один Flutter-код на три платформы (Linux/Windows/Android — единственный стек, дающий это без компромиссов по UI). Вся "трудная" часть — P2P-транспорт и слияние конфликтов — закрывается готовыми библиотеками, свой код нужен только для UI, бизнес-логики и склейки модулей между собой.

## 3. Стек и готовые компоненты (главное — что НЕ надо писать самому)

| Задача | Готовый компонент | Что он даёт из коробки |
|---|---|---|
| UI-фреймворк | **Flutter** | Один код на Linux/Windows/Android, нативная производительность |
| Управление состоянием | **Riverpod** | Реактивная архитектура, DI, без своего велосипеда |
| Аудиодвижок (воспроизведение) | **media_kit** (на основе libmpv) | Реально работает на Linux и Windows (в отличие от just_audio, у которого там дыры), поддерживает MP3/FLAC/OGG/всё что знает mpv, GPU-рендеринг обложек/визуализации |
| Уведомления/lockscreen/Bluetooth-кнопки на Android | **audio_service** | Готовая интеграция с системным медиа-центром Android, не нужно писать нативный код |
| Чтение/запись ID3-тегов | **id3** (чистый Dart, работает в VM/Flutter/Web одинаково) | Разбор/запись жанра, альбома, исполнителя, обложки без FFI и без проблем с кроссплатформенностью |
| **CRDT-слияние данных (самое сложное место)** | **crdt + sql_crdt + sqlite_crdt** (пакеты cachapa) | Готовая Dart-нативная реализация CRDT поверх SQLite с Hybrid Logical Clocks: soft-delete (tombstone), автоматическое разрешение конфликтов по полям, история изменений — именно то, что нужно для избранного/тегов/плейлистов, отредактированных офлайн на разных устройствах |
| **Сетевая синхронизация CRDT-узлов** | **crdt_sync** (тот же автор, "turnkey" под sql_crdt) | Готовый протокол обмена изменениями между узлами — не нужно самому придумывать формат дельт и порядок применения |
| Обнаружение устройств в LAN | **bonsoir** или **multicast_dns** | Готовый mDNS/Bonjour discovery на всех трёх платформах |
| Передача самих аудиофайлов | **Syncthing как внешний процесс** + его REST API через обычный `http`/`dio` пакет | Не пишем свой протокол передачи файлов и chunked transfer — Syncthing уже поставляется под Linux/Windows/Android, его достаточно дергать по локальному REST API (localhost:8384) |
| Локальное хранилище/кеш | **sqlite_crdt** (уже включает SQLite-слой) | Отдельный слой не нужен — БД и CRDT это один и тот же пакет |
| Безопасное хранение ключей устройства | **flutter_secure_storage** | Keychain/EncryptedSharedPreferences под капотом |

Единственное, для чего готового Flutter-пакета не нашлось — аудио-фингерпринтинг (дедупликация одинаковых треков с разными именами файлов). Здесь придётся либо написать тонкий FFI-биндинг к `libchromaprint` (C-библиотека, сама по себе готовая и стабильная, просто нет Dart-обвязки), либо вынести эту функцию за скобки MVP и дедуплицировать по более грубому критерию (имя+длительность+битрейт) на первом этапе.

## 4. Разделение труда: что берёт на себя каждый готовый компонент

```
┌─────────────────────────────────────────┐
│         Flutter UI (свой код)            │
│   вкладки, мини-плеер, обложки, поиск    │
└──────────────┬────────────────────────────┘
               │
   ┌───────────┴────────────┐
   │                         │
┌──▼───────────┐   ┌─────────▼─────────┐
│ media_kit     │   │  sqlite_crdt +     │
│ (воспроизв.)  │   │  crdt_sync         │
│               │   │  (метаданные:      │
│               │   │  жанры/избранное/  │
│               │   │  плейлисты)        │
└───────────────┘   └─────────┬─────────┘
                                │ синк дельт
                     ┌──────────▼──────────┐
                     │  bonsoir (discovery) │
                     └──────────┬──────────┘
                                │
                     ┌──────────▼──────────┐
                     │ Syncthing (файлы)     │
                     │ REST API локально    │
                     └───────────────────────┘
```

Свой код нужен в основном как "клей": UI-слой, маппинг между CRDT-таблицами и виджетами, логика запуска/мониторинга Syncthing-процесса, обработка событий discovery.

## 5. Модель данных (таблицы в sqlite_crdt)

- `tracks` — id (по возможности хеш файла), путь, название, исполнитель, альбом, жанр, длительность, обложка (путь/blob), добавлен_на_устройстве
- `favorites` — track_id, is_favorite (bool) — простое поле, CRDT-слой сам разрешает конфликт по HLC
- `playlists` — id, название
- `playlist_tracks` — playlist_id, track_id, позиция (для упорядоченных списков нужно закладывать явное поле порядка, а не полагаться на порядок вставки — при слиянии двух офлайн-правок порядок вставки не детерминирован)
- `devices` — id устройства (публичный ключ), имя, последний онлайн

Все таблицы автоматически получают от sql_crdt служебные поля `is_deleted`, `hlc`, `modified` — писать эту логику вручную не требуется.

## 6. Функциональные требования (UI в духе Яндекс Музыки)

1. **Нижний мини-плеер**, разворачивающийся в полноэкранный плеер свайпом вверх — обложка, прогресс-бар, кнопки избранного/очереди.
2. **Вкладки**: Библиотека (треки/альбомы/жанры/исполнители), Плейлисты, Поиск, Устройства (статус синхронизации).
3. **Экран "Устройства"**: список известных узлов, статус online/offline, ручной запуск синхронизации, QR-код для добавления нового устройства (используя публичный ключ как ID).
4. **Импорт новых треков**: файловый пикер/наблюдение за папкой загрузок → автоматическое извлечение ID3-тегов → запись в `tracks` → CRDT-дельта автоматически уйдёт на другие устройства при следующем синке.
5. **Избранное**: тап по сердечку → мгновенное обновление локально (offline-first) → фоновая синхронизация без блокировки UI.
6. **Индикатор конфликта** (редкий, но должен быть предусмотрен в UI): если сеть была разделена долго и есть расхождения, показывать ненавязчивый бейдж "синхронизировано N изменений" — без этого пользователь не поймёт, что вообще произошло слияние.

## 7. Нефункциональные требования

- Полностью офлайн-first: приложение полностью функционально без сети, синхронизация — это фоновый бонус, а не блокирующая операция.
- Синхронизация должна запускаться автоматически при обнаружении известного устройства в сети (через bonsoir), без ручных действий пользователя.
- Никаких сторонних облачных сервисов и телеметрии.

## 8. Этапы разработки (MVP → полная версия)

1. **Этап 0**: UI-каркас на Flutter + media_kit, чтение локальной папки, отображение библиотеки, без синхронизации.
2. **Этап 1**: подключение sqlite_crdt для хранения метаданных локально (ещё без сети) — миграция с "просто файлов" на CRDT-таблицы.
3. **Этап 2**: интеграция crdt_sync + bonsoir — синхронизация метаданных между устройствами в LAN.
4. **Этап 3**: интеграция с Syncthing REST API — автоматический перенос самих аудиофайлов.
5. **Этап 4**: дедупликация (сначала грубая эвристика, затем — при необходимости — FFI-биндинг к chromaprint).
6. **Этап 5**: полировка UI под референс Яндекс Музыки, анимации, обложки, тёмная тема.

## 9. Риски

- **media_kit** на Linux требует системных библиотек mpv — на этапе установки нужен либо bundling, либо явное указание зависимости в инструкции для пользователя.
- **Syncthing как внешний процесс** — на Android его придётся встраивать как foreground-сервис (есть форк syncthing-android с открытым кодом, который можно использовать как референс или встроить как зависимость).
- Порядок элементов в плейлистах — единственное место, где "из коробки" CRDT-таблицы сами не решат конфликт идеально; тут нужно либо принять "eventual consistency" с редкими визуальными перестановками, либо реализовать поверх более сложную структуру (RGA), что уже собственный код.
