# Модель данных

Хранилище — `sqlite_crdt` (см. [ADR 0003](adr/0003-cachapa-crdt-suite-for-local-storage.md)).
Схема создаётся в `lib/data/db/audiloc_database.dart`. Файл БД живёт
по адресу `<appSupportDir>/profiles/<profileId>/audiloc.db` — своя
база (и свой `nodeId`, см. [ADR 0006](adr/0006-device-identity-without-asymmetric-crypto.md))
на каждый профиль устройства, см. [ADR 0013](adr/0013-account-profiles.md).
Всё описанное ниже (таблицы, CRDT-поля) — про содержимое ровно одной
такой базы, то есть ровно одного профиля.

Каждая таблица ниже **автоматически** получает от `sql_crdt` четыре
служебных столбца — их не нужно объявлять и не нужно писать руками:

| Столбец | Тип | Смысл |
|---|---|---|
| `is_deleted` | INTEGER | Soft-delete: `DELETE` переписывается в `UPDATE ... SET is_deleted = 1` |
| `hlc` | TEXT | Hybrid Logical Clock записи — используется при слиянии для выбора "победителя" |
| `node_id` | TEXT | Id устройства, сделавшего последнюю запись |
| `modified` | TEXT | HLC последнего изменения — по нему идёт `getChangeset`/`merge` |

## `tracks`

| Столбец | Тип | Смысл |
|---|---|---|
| `id` (PK) | TEXT | SHA-256 хеш содержимого файла — см. ниже "Почему хеш, а не UUID" |
| `path` | TEXT | Путь, под которым файл импортировало **последнее по HLC** устройство — сырой столбец, приложение его не читает напрямую, см. `track_locations` ниже |
| `title`, `artist`, `album`, `genre` | TEXT? | Из тегов (`audiotags`, [ADR 0002](adr/0002-audiotags-instead-of-id3.md)) |
| `duration_ms` | INTEGER? | Best-effort из тегов; `media_kit` даёт точное значение в рантайме |
| `bitrate_kbps` | INTEGER? | Зарезервировано; `audiotags` его сейчас не отдаёт |
| `cover_path` | TEXT? | Сырой столбец, приложение его не читает напрямую — только как признак "у какого-то устройства есть обложка", см. `track_locations` ниже и [ADR 0012](adr/0012-local-cover-paths.md) |
| `file_size` | INTEGER? | Байты; резерв для более точной дедупликации в будущем |
| `added_on_device` | TEXT? | Id устройства, первым импортировавшего файл |

### Почему хеш файла, а не UUID

ТЗ п.5 явно предлагает "id (по возможности хеш файла)". Хеш даёт
идемпотентный повторный импорт: тот же файл, добавленный дважды (в
том числе на другом устройстве, под другим путём), получает тот же
`id` и просто обновляет существующую строку вместо дублирования.

## `track_locations`

| Столбец | Тип | Смысл |
|---|---|---|
| `id` (PK) | TEXT | `'$trackId:$nodeId'` — составной ключ, см. ниже почему |
| `track_id` | TEXT | Ссылается на `tracks.id` |
| `path` | TEXT | Путь к аудиофайлу **на этом конкретном устройстве** — с [ADR 0014](adr/0014-always-copy-imports-and-ui-redesign.md) это всегда путь внутри собственного хранилища приложения, независимо от того, докачан ли файл с пира или импортирован вручную; никогда не оригинальный путь, который выбрал пользователь |
| `cover_path` | TEXT? | Путь к закэшированной обложке **на этом конкретном устройстве** — та же идея, что и `path`, см. [ADR 0012](adr/0012-local-cover-paths.md). Может быть NULL, даже когда `path` уже есть: устройство вполне может иметь аудио без обложки, пока та не докачалась |

`path` умышленно **не** входит в идентичность трека и задумывался как
локальный для устройства с самого начала — но `tracks.path` сам по
себе этого не гарантирует: `sql_crdt` разрешает конфликты по строке
целиком, так что при обычном столбце `path` победитель по HLC
переписывает путь **для всех устройств разом**, а не только для
"своего". Два устройства, независимо импортировавшие один и тот же
файл (одинаковый `id`) из разных папок, после синка внезапно получали
чужой, физически не существующий путь — и плеер молча пропускал
трек и включал следующий в очереди, создавая ощущение "играет
случайная музыка". См. [ADR 0009](adr/0009-local-track-paths.md).

Ключ `'$trackId:$nodeId'` (а не просто `track_id`) — единственный
способ в этой CRDT-модели дать каждому устройству *свою* строку,
которую слияние с чужими записями не заденет: конфликты `sql_crdt`
разрешает по первичному ключу, а он у каждого устройства свой.
`TracksRepository`/`PlaylistsRepository` при чтении резолвят оба пути
через `LEFT JOIN ... tl.path AS path, tl.cover_path AS cover_path`,
отфильтрованный по `node_id` текущего устройства — **без** отката на
`tracks.path`/`tracks.cover_path`: если у этого устройства нет
собственной строки в `track_locations`, `Track.path`/`Track.coverPath`
в модели приходят `null` (`Track.isAvailableLocally == false` для
аудио), а не чужой, физически не существующий на этом устройстве
путь. Трек без аудио попадает в `TracksRepository.watchMissingFiles()`,
и `FileSyncService` докачивает файл с первого online-пира, у которого
он есть (`peersWithLocalCopy()`) — см.
[ADR 0010](adr/0010-built-in-file-transfer.md). Трек с аудио, но без
локальной обложки — в `watchMissingCovers()`, докачивается отдельно
`CoverSyncService` ([ADR 0012](adr/0012-local-cover-paths.md)). После
успешной докачки `TracksRepository.recordLocalFile()`/`recordLocalCover()`
пишут строку в `track_locations`, и файл становится доступным локально.

## `favorites`

| Столбец | Тип | Смысл |
|---|---|---|
| `track_id` (PK) | TEXT | Ссылается на `tracks.id` (без FK-constraint — soft-delete делает строгие FK неудобными) |
| `is_favorite` | INTEGER | 0/1 |

Отдельная таблица от `tracks` — намеренно (ТЗ п.5): тап по сердечку
на одном устройстве не должен конкурировать по HLC с правкой тега на
другом для той же строки `tracks`.

## `playlists`

| Столбец | Тип | Смысл |
|---|---|---|
| `id` (PK) | TEXT | UUID v4 |
| `name` | TEXT | |
| `cover_track_id` | TEXT? | Ссылка на `tracks.id`, когда обложка плейлиста — обложка одного из его же треков (обычная синхронная колонка-ссылка, безопасна как есть — реальный путь резолвится через `track_locations`, см. выше); `NULL`, если обложка — картинка из файла или её нет вовсе |

## `playlist_locations`

| Столбец | Тип | Смысл |
|---|---|---|
| `id` (PK) | TEXT | `'$playlistId:$nodeId'` — тот же составной-ключ трюк, что у `track_locations`, и по той же причине |
| `playlist_id` | TEXT | Ссылается на `playlists.id` |
| `cover_path` | TEXT? | Путь к кастомной картинке-обложке (не из тегов трека) **на этом конкретном устройстве** |

Точный аналог `track_locations`, только для случая "обложка плейлиста
— картинка из файла", а не одна из обложек его треков
(`playlists.cover_track_id` выше). Синхронизация самого файла между
устройствами одного профиля для этого случая **не реализована** —
осознанное сокращение объёма, картинка видна только там, где её
выбрали (см. [ADR 0017](adr/0017-forbid-cross-profile-pairing-and-sharing.md)).

## `playlist_tracks`

| Столбец | Тип | Смысл |
|---|---|---|
| `id` (PK) | TEXT | UUID v4 — суррогатный ключ, не `(playlist_id, track_id)` |
| `playlist_id` | TEXT | |
| `track_id` | TEXT | |
| `position` | REAL | Дробный порядок (fractional indexing) |

Суррогатный `id` (а не составной PK) допускает несколько вхождений
одного трека в плейлисте и даёт стабильную "ручку" для удаления
именно этого вхождения (`PlaylistItem.entryId`,
`PlaylistsRepository.removeEntry`).

### Порядок и его пределы (ТЗ п.9)

`position` — дробное число. Вставка/перемещение трека пишет **только
эту одну строку**, вычисляя позицию как середину между соседями
(`PlaylistsRepository.moveEntry`, шаг по умолчанию 1000 при
добавлении в конец). Это дешевле, чем перезаписывать позиции всех
треков, и в подавляющем большинстве случаев не конфликтует при
слиянии офлайн-правок с разных устройств.

Это **не** полноценная CRDT-структура для порядка (RGA/список с
операциями vставки, устойчивыми к любому интерливингу). ТЗ прямо
называет это единственным местом, где "из коробки" CRDT-таблицы не
решают конфликт идеально (п.9): если два устройства одновременно
переставят один и тот же трек в разные позиции офлайн, слияние
оставит один из результатов по HLC — глазами пользователя это редкая
"визуальная перестановка", не потеря данных. Настоящий RGA поверх
этого — в docs/roadmap.md.

## `devices`

| Столбец | Тип | Смысл |
|---|---|---|
| `id` (PK) | TEXT | `SqliteCrdt.nodeId` этого устройства — см. [ADR 0006](adr/0006-device-identity-without-asymmetric-crypto.md) |
| `name` | TEXT | `"<имя профиля> (<платформа/модель>)"` — не голое имя профиля, чтобы два устройства одного профиля были различимы в списке ([ADR 0016](adr/0016-device-label.md)) |
| `host` | TEXT? | Последний известный LAN-адрес (из mDNS-резолва) |
| `sync_port` | INTEGER? | Порт `MetadataSyncService` на этом узле |
| `last_online_at` | INTEGER? | Epoch millis последнего "увиделись" |

Столбец `syncthing_device_id` физически остаётся в SQL-схеме (никем
не читается и не пишется на уровне Dart-модели `Device`) — не
мигрировали, чтобы не усложнять схему ради столбца, который просто
лежит без дела; см. [ADR 0010](adr/0010-built-in-file-transfer.md).

**Online/offline статус в этой таблице не хранится.** Это живое
состояние из `DiscoveryService.events`, собираемое в
`onlineDeviceIdsProvider` — намеренное разделение "что мы знаем о
устройстве" (персистентно) от "видим ли мы его прямо сейчас"
(эфемерно, теряется при перезапуске и это нормально).

## `playback_state`

| Столбец | Тип | Смысл |
|---|---|---|
| `id` (PK) | TEXT | Всегда буквально `'current'` — таблица нарочно содержит **ровно одну строку** |
| `track_id` | TEXT | Ссылается на `tracks.id` |
| `position_ms` | INTEGER | Позиция в треке на момент паузы |
| `queue_type` | TEXT | `library` / `favorites` / `playlist` |
| `playlist_id` | TEXT? | Только для `queue_type = 'playlist'` |
| `device_id` | TEXT | Кто написал последнюю запись — `devices.id` |
| `device_name` | TEXT | Имя устройства на момент записи (для текста уведомления "Продолжить с..., Устройство?") |

Единственная строка (`id = 'current'`) — сознательный трюк: обычное
CRDT-разрешение конфликтов по HLC **на уровне строки** (не столбца)
само по себе даёт "синхронизируется только самое последнее состояние"
бесплатно, без отдельной логики поверх мержа. Пишется **только по
паузе** (не на каждый тик позиции — тот же урок про write-storm, что
уже был с `devices.last_online_at`, [ADR 0025](adr/0025-sync-and-discovery-reliability.md))
и при закрытии приложения во время воспроизведения. Управляется одним
профильным тумблером синка (`profile_settings.sync_playback_enabled`
ниже, выключен по умолчанию, отдельно от восстановления собственной
сессии — см. ниже): пока он выключен, устройство не пишет в эту
таблицу и не реагирует на чужие строки в ней; когда включён — входящая
строка от **другого** устройства молча применяется, если здесь ничего
не загружено, иначе спрашивает через уведомление. Изначально это были
два раздельных device-local тумблера "отправлять"/"принимать" —
объединены в один профильный, см. [ADR 0032](adr/0032-unified-profile-sync-and-background-mode.md).
См. [ADR 0029](adr/0029-playback-state-sync.md).

## `profile_settings`

| Столбец | Тип | Смысл |
|---|---|---|
| `id` (PK) | TEXT | Всегда буквально `'current'` — тот же трюк "ровно одна строка", что у `playback_state` выше |
| `sync_playback_enabled` | INTEGER | 0/1 — единый профильный тумблер, включает/выключает и запись, и приём `playback_state` выше, и весь протокол эксклюзивного владения воспроизведением (см. `playback_ownership/` в [`docs/architecture.md`](architecture.md)) |

Единственная профильная (не device-local) настройка в CRDT-базе —
именно поэтому она здесь, а не в `settings.json` (`AppSettingsStore`,
ниже): включение на одном устройстве должно быть видно на всех
устройствах профиля после синка, а не решаться каждым устройством за
себя. См. [ADR 0032](adr/0032-unified-profile-sync-and-background-mode.md).

## Не-CRDT локальные хранилища

Не всё, что приложение сохраняет, живёт в CRDT-базе — часть состояния
намеренно **не** синхронизируется и хранится обычными файлами:

- `<appSupportDir>/settings.json` (`AppSettingsStore`) — уровня
  устройства, не профиля: тема, язык, настройки клавиатурных
  шорткатов, "разрешить удалённое управление"
  ([ADR 0030](adr/0030-remote-playback-control.md)). Общее для всех
  профилей на этом устройстве, переживает переключение профиля. Синк
  `playback_state` выше управляется отдельно, профильным тумблером в
  CRDT (`profile_settings` выше), не отсюда.
- `<appSupportDir>/profiles/<profileId>/last_session.json`
  (`LocalPlaybackStateStore`) — тот же набор полей, что у
  `playback_state` выше, но профиль-скоуп и никогда никуда не
  синкается: чисто локальное "что играло здесь последний раз",
  никак не связанное с профильным тумблером синка выше. Включено по
  умолчанию (тумблер "Сохранять состояние прошлой сессии" в
  Настройках) — восстановление после перезапуска работает даже когда
  вся сетевая синхронизация состояния выключена. См.
  [ADR 0029](adr/0029-playback-state-sync.md).
