# 0009. `track_locations`: путь к файлу — локальное поле, не синхронизируемое

## Контекст

Первая живая проверка на двух физических устройствах (Android +
Linux, после фикса из [ADR 0005](0005-crdt-sync-for-p2p-metadata.md))
показала: после того как синк заработал, на Android иногда начинал
играть совсем не тот трек, по которому тапнули.

Причина: `tracks.path` — обычный синхронизируемый столбец. Оба
устройства независимо импортировали один и тот же файл (одинаковый
sha256 → одинаковый `id`, [ADR 0003](0003-cachapa-crdt-suite-for-local-storage.md))
из своих локальных папок — на Android это, например,
`/storage/emulated/0/Music/song.mp3`, на Linux —
`/home/user/Music/song.mp3`. `sql_crdt` разрешает конфликты **по
строке целиком**: чья запись "моложе" по HLC, та и побеждает
полностью, включая `path`. После синка Android мог получить
Linux-путь — файла с таким путём на телефоне физически не существует.
`media_kit`/mpv на нерабочем файле в очереди не падает с ошибкой, а
молча пропускает его и включает следующий трек — отсюда ощущение
"играет что-то совсем другое".

Это прямое нарушение того, что уже было задумано в
[data-model.md](../data-model.md) ("`path`... локален для устройства
и может законно отличаться между узлами") — задокументировано с
самого начала, но фактически не обеспечено реализацией: сама
семантика merge в `sql_crdt` не различает "синхронизируемые" и
"локальные" столбцы внутри одной строки.

## Решение

Новая таблица `track_locations`: `id` (=`'$trackId:$nodeId'`),
`track_id`, `path`. Ключ намеренно составной (через `nodeId`) — это
единственный способ в модели cachapa CRDT дать каждому устройству
"свою" строку, которую слияние с чужими записями не тронет: `sql_crdt`
конфликтует по первичному ключу, а он у каждого устройства свой.

Чтение (`TracksRepository`, `PlaylistsRepository`) резолвит путь через
`LEFT JOIN ... COALESCE(tl.path, t.path)`, фильтруя `track_locations`
по `nodeId` текущего устройства. `TracksRepository.upsert()` при
каждом импорте пишет и в `tracks`, и в `track_locations` — вызывающий
код (`LibraryImportService`) не меняется.

`tracks.path` как столбец остаётся (нужен для `NOT NULL`/истории,
и как значение по умолчанию, если у устройства ещё нет собственной
строки в `track_locations`).

## Последствия

- Устройство, которое **само** импортировало файл, после любого
  синка продолжает играть свою локальную копию — даже если другое
  устройство синхронизировало метаданные позже.
- Устройство, которое узнало о треке **только через синк** (файл ещё
  не пришёл, например, через Syncthing), при отсутствии собственной
  записи в `track_locations` по-прежнему получает чужой (нерабочий)
  путь через `COALESCE`-фоллбэк на `t.path` — то есть проблема не
  устранена полностью для этого случая, только для "уже
  импортировал сам". Правильный фикс — `Track.path` как `String?`
  и явный UI-статус "файл ещё не доступен локально" — отложен как
  более крупный рефакторинг, роадмап-пункт.
- Требуется миграция схемы (`version: 1` → `2`,
  `AudilocDatabase._upgradeSchema`) — учтено, но не проверялось на
  реальном апгрейде уже установленного приложения (только на
  свежих БД).
