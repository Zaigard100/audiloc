# 0014. Импорт всегда копирует файл + редизайн навигации

## Контекст

Запрошенный пользователем редизайн затронул несколько независимых, но
связанных решений — сгруппированы в один ADR, так как принимались
вместе и объясняют друг друга.

## Импорт всегда копирует в собственное хранилище приложения

До этого ADR `LibraryImportService` писал в `tracks.path` буквально
путь, который выбрал пользователь (папка/файл) — трек проигрывался
прямо оттуда. По явной просьбе пользователя (подтверждено через
AskUserQuestion) это изменено: **любой** импорт — и через "Добавить
папку", и через новую "Добавить трек" — теперь копирует файл в
собственное хранилище приложения (`syncedMusicDirProvider`'s
директория — та же, куда `FileSyncService` уже кладёт P2P-докачанные
треки, см. [ADR 0010](0010-built-in-file-transfer.md)) и пишет в
`tracks.path` путь **туда**, не к оригиналу пользователя.

- Копия, не перемещение — `File.copy`, не `rename`/удаление
  оригинала. Импорт не должен незаметно менять файлы пользователя вне
  приложения.
- Имя файла в хранилище — `$id<расширение>`, тот же паттерн, что уже
  использует P2P-докачка (`FileTransferClient.download`) и кэш
  обложек (`$id.cover`) — раз `id` это sha256 контента, коллизий с
  чужой докачкой той же самой песни быть не может, а повторный импорт
  идентичных байт просто находит уже существующую копию
  (`if (!await dest.exists())`).
- Уже импортированные до этой правки треки **не** мигрируются — они
  по-прежнему рабочие, просто по старому (внешнему) пути; миграция
  сознательно не в объёме этой правки.
- Последствие: и синканные с других устройств, и вручную добавленные
  файлы теперь физически лежат в одном месте и по одной и той же
  логике становятся "доступны локально" — `Track.isAvailableLocally`
  больше не подразумевает "где-то на диске пользователя", а всегда
  "в собственном хранилище приложения".

## "Стереть навсегда" — что это реально может означать

См. подробности в докстринге `TracksRepository.eraseFileFromDisk` —
кратко: `sql_crdt` не даёт настоящего построчного `DELETE`, поэтому
"навсегда" может означать только "стереть локальную копию с диска
этого устройства", не "стереть у всех". Восстановление после этого
переводит трек в обычное состояние "нет локального файла — ждёт
докачки", как у любого другого ещё не докачанного трека.

## Редизайн навигации

- **Библиотека** — только плоский, сортируемый (Название/Исполнитель/
  Дата добавления, оба направления) список всех треков. Жанры убраны
  полностью — не только вкладка, сам концепт группировки по жанру
  (`genresProvider`/`tracksByGenreProvider`/`allGenres()`/
  `GenreTracksScreen` — всё удалено, не просто скрыто).
- **Плейлисты** — сетка квадратов (`GridView`, 2 колонки), а не
  список. "Избранное" и "Удалённые" — специальные карточки, всегда
  первые двумя, ведут на `FavoritesScreen`/`TrashScreen`
  (обычный `Navigator.push`, без go_router-маршрута — они не
  диплинкаются, как и `FullPlayerScreen`).
- **Избранное** сортируется по дате добавления в избранное, новые
  сверху — `FavoritesRepository.watchFavoritedAt()` читает `modified`
  таблицы `favorites` (обновляется при каждом тапе по сердечку).
  Ручного drag-reorder там нет — нет колонки порядка, это живое
  представление.
- **Плейлисты (настоящие)** получили drag-and-drop переупорядочивание
  — инфраструктура (`PlaylistsRepository.moveEntry`, дробный
  `position`) уже существовала, не хватало UI
  (`ReorderableListView.builder` + `PlaylistItem.position`,
  добавленное в `watchItems()`).
- **Полноэкранный плеер** показывает, откуда играет очередь —
  "Играет: Библиотека" / "Играет: Избранное" / "Играет: Плейлист
  «Имя»". Новый лёгкий `queueSourceProvider`
  (`lib/features/player/providers/player_providers.dart`), не
  изменяющий `PlayerService`/`media_kit` — чисто UI-метка, которую
  выставляет каждый вызывающий `setQueue(...)` код рядом с самим
  вызовом.
- **QR-код** на вкладке Устройства убран целиком (и зависимость
  `qr_flutter`) — он никогда не был частью реального пути сопряжения
  (сканера для его чтения не было), сопряжение всегда шло через
  discovery + подтверждение
  ([ADR 0011](0011-mutual-pairing-confirmation.md)); экран с QR
  только добавлял лишний путь без добавления функциональности.

## Последствия

- `Track.modifiedAt` — новое поле, "лучшее приближение" даты
  добавления, вычисляется из уже существующей CRDT-колонки `modified`
  (`.toHlc.dateTime`), без миграции схемы.
- Сортировка библиотеки и избранного — чисто in-memory (`List.sort`
  над уже загруженным списком), без новых SQL-запросов — библиотека
  это личная коллекция (сотни/тысячи, не миллионы записей).
