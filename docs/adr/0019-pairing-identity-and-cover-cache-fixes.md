# 0019. Четыре бага с живой проверки: identity сопряжения, кэш обложек, удаление профиля

## Контекст

Живая проверка после релиз-кандидата 1.0.0-rc.1 нашла четыре реальных
бага:

1. При сопряжении через "Ждать сопряжения" устройство меняет имя, но
   старое "Новое устройство" остаётся висеть где-то ещё.
2. При редактировании обложки трека новая картинка не появляется ни в
   превью диалога, ни после сохранения — только после перезапуска
   приложения.
3. Удалённый профиль всё ещё виден в переключателе, пока не закрыть и
   не открыть его заново.
4. После удаления профиля часть файлов (как минимум один трек) не
   стирается с диска.

## Решение

### 1. Сопряжение: identity меняется, старая запись — нет

Корень: `PairingService.approve()` отвечал на входящий запрос **до**
переключения профиля, используя ещё старую (плейсхолдер) identity —
`_selfId`/`_selfName` в вызывающем сеансе. Но CRDT node id
привязан к конкретному файлу базы (docs/adr/0013-account-profiles.md),
а не к устройству — после переключения на другой профиль это
**другая** база с **другим** node id. Запросившая сторона получала
ответ под старым id и создавала `devices`-запись под ним; после
переключения запись под новым id появлялась (если вообще появлялась —
синк между новой сессией и пиром ещё должен быть авторизован) отдельно
— две записи на одно физическое устройство, старая никогда не
подчищается.

Исправлено: `approve()` для несовпадающего хэша теперь **не отвечает
вообще** — только вызывает `onJoinDifferentProfile`. Переключение
профиля (`AudilocApp._joinProfileForPairing`) после смены сессии
вызывает `approve(request)` **повторно**, уже на новой
`PairingService` — к этому моменту хэш совпадает по построению, так что
он проходит через обычную ветку "тот же профиль": отвечает и
сопрягается один раз, под identity, которая действительно останется.
`pairWithoutResponding` (использовавшийся раньше именно для этого)
удалён — больше не нужен, повторный `approve()` делает то же самое
корректно.

### 2. Обложка трека/плейлиста не обновлялась без перезапуска

`Image.file` использует `FileImage`, чей ключ в глобальном
`imageCache` — это путь файла, а не его содержимое. И
`edit_track_dialog.dart`, и `playlist_cover_picker.dart` копировали
новую картинку в **тот же самый** путь, что уже был закэширован
(`<id>.cover`) — поэтому ни диалог, ни список треков/плейлистов не
видели изменения: Flutter отдавал старые декодированные байты из кэша
по тому же ключу. Помогал только перезапуск, потому что `imageCache` —
чисто in-memory.

Исправлено: каждая новая выбранная картинка сохраняется под уникальным
именем (`<id>-<timestamp>.cover`), а не перезаписывает старый файл —
гарантированный промах кэша везде, где отображается обложка, без
ручной инвалидации.

### 3 и 4. Удаление профиля: список не обновляется, файлы остаются

Оба бага — один и тот же корень.
`ProfileSwitcherSheet._deleteDialog` вызывал `_refresh()` **после**
`ProfilesStore.delete(...)`, но ничего не ловило исключение, если
стирание директории бросало ошибку — а `Directory.delete(recursive:
true)` останавливается на **первой же** проблемной записи и бросает
исключение, даже не пытаясь стереть остальное. Необработанное
исключение в необожидаемом (`onPressed: () => _deleteDialog(...)`)
асинхронном вызове тихо проглатывалось фреймворком — `_refresh()`
никогда не выполнялся (объясняет баг 3: запись в `profiles.json` уже
обновлена, поэтому при **повторном открытии** шита — свежий
`initState` — профиль корректно пропадал), а из директории стиралось
только то, что успело до первой ошибки (объясняет баг 4).

Исправлено на двух уровнях:
- `ProfilesStore._eraseDirectory` — ручной рекурсивный обход вместо
  одного вызова `Directory.delete(recursive: true)`: удаляет каждую
  запись по отдельности, продолжая после ошибки на любой из них, и
  бросает первую пойманную ошибку только в самом конце — так один
  залоченный файл (например, ещё не отпущенный плеером трек, недавно
  игравший из этого профиля) не блокирует удаление всего остального.
- `ProfileSwitcherSheet._deleteDialog` — `try/catch/finally`:
  `_refresh()` теперь выполняется всегда, а реальная ошибка (если
  что-то всё же не удалось стереть) показывается через `SnackBar`
  вместо тихого исчезновения.
