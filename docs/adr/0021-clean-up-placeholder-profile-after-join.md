# 0021. Профиль-заглушка "Новое устройство" убирается после присоединения

## Контекст

После [ADR 0017](0017-forbid-cross-profile-pairing-and-sharing.md)/
[0020](0020-wait-for-pairing-from-switcher.md) поток "Ждать
сопряжения" работал корректно с точки зрения библиотеки — устройство
успешно переключалось на профиль инициатора и скачивало его
содержимое. Но сам плейсхолдер "Новое устройство"
(`ProfilesStore.create('Новое устройство')` из `_waitForPairing`)
никогда не удалялся из реестра — он просто переставал быть активным.
Пользователь заметил: в переключателе профилей навсегда остаётся
бесполезная пустая запись "Новое устройство".

## Решение

`AudilocApp._joinProfileForPairing` теперь запоминает, было ли
устройство именно в состоянии ожидания (`_awaitingProfileAdoption`,
захватывается **до** `_switchProfile`, которая сбрасывает этот флаг
одним из первых шагов) и id профиля, с которого уходим. Если это
действительно был плейсхолдер и произошло реальное переключение —
после `_switchProfile` вызывается `store.delete(oldProfileId)`
(`ProfilesStore.delete()`, теперь безвозвратно стирающий директорию —
см. [ADR 0018](0018-delete-profile.md)).

Безусловное удаление, без проверки "точно ли профиль пуст": плейсхолдер
создаётся исключительно ради этого одного ожидания и ни для чего
больше не предназначен — весь смысл кнопки в том, что это одноразовая
заглушка. Если пользователь всё же успел что-то добавить в неё за
время ожидания — редкий случай не в духе задуманного использования,
не стоящий добавления отдельной проверки "пуст ли профиль" (открытия
его базы только ради этой проверки).

## Последствия

- После завершения "Ждать сопряжения" в переключателе профилей видно
  только реальные профили — ни одной осиротевшей заглушки.
- Прямых unit-тестов на `_joinProfileForPairing` в проекте нет (это
  приватный метод `AudilocApp`, оркестрирующий несколько сервисов) —
  как и остальная его логика, проверяется вживую.
