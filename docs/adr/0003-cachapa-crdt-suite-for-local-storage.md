# 0003. `crdt` + `sql_crdt` + `sqlite_crdt` (cachapa) для локального хранения

## Контекст

Метаданные (треки, избранное, плейлисты, устройства) редактируются
офлайн на нескольких устройствах и должны сливаться без конфликтов
при последующей синхронизации — ровно то, что ТЗ называет «самым
сложным местом» (п.3).

## Решение

Пакеты cachapa (`crdt`, `sql_crdt`, `sqlite_crdt`) — готовая
Dart-нативная реализация CRDT поверх SQLite с Hybrid Logical Clocks:

- Каждая таблица автоматически получает `is_deleted`, `hlc`,
  `node_id`, `modified` — не нужно писать эту бухгалтерию руками
  (см. docs/data-model.md).
- Конфликты по строке разрешаются по наибольшему HLC на `merge()`
  (`sql_crdt`'s `CrdtExecutor`), без ручной логики "last write wins"
  в коде приложения.
- `SELECT`/`INSERT`/`UPDATE`/`DELETE` — обычный SQL; `DELETE`
  автоматически переписывается в soft-delete (`is_deleted = 1`).

## Последствия

- ID узла (`SqliteCrdt.nodeId`) не хранится отдельно — он
  восстанавливается из HLC последней записанной строки при открытии
  БД. Из этого следует: для стабильного id устройства нужна хотя бы
  одна запись сразу при первом запуске — см. 0006.
- Порядок треков в плейлисте — единственное место, где "из коробки"
  это не даёт идеального слияния (см. docs/data-model.md,
  `playlist_tracks.position`); ТЗ п.9 прямо об этом предупреждает.
- Тестируется полностью офлайн через `SqliteCrdt.openInMemory()` —
  без сети и без файловой системы, что сделало репозитории лёгкими
  для unit-тестов (test/unit/data/*).
