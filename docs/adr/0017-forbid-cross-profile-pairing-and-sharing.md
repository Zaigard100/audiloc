# 0017. Сопряжение — только один и тот же профиль; "Поделиться" — для остального

## Контекст

[ADR 0015](0015-profile-identity-in-pairing.md) научило сопряжение
"добавлять устройство в профиль": если хэши профилей не совпадали,
принимающая сторона переключалась на (копию) профиля инициатора и
скачивала его библиотеку. Пользователь явно попросил это запретить:
сопряжение разных пользователей не должно быть возможным вообще.
Взамен нужен более лёгкий, явный способ передать конкретный трек или
альбом другому, в т.ч. чужому, профилю — "Поделиться" — с превью на
принимающей стороне перед тем, как что-либо появится в его библиотеке.

Отдельно пользователь отметил два пробела в UI (долгий тап по треку
сразу удалял, без выбора действия; у плейлистов не было ни
переименования, ни удаления, ни обложки через UI, хотя два первых
метода в `PlaylistsRepository` уже существовали) и попросил добавить
их же по правому клику на десктопе, не только по долгому тапу.

## Решение

### Сопряжение снова строго "тот же профиль/устройство"

Сравнение хэшей осталось (оно и так уже нужно для сценария A из ADR
0013 — "Ждать сопряжения"), но теперь оно **фильтрует входящие запросы
до того, как они попадают в UI**, а не решается пользователем в
диалоге:

- `PairingService` слушает `_server.requests` сам (не отдаёт поток
  напрямую) и решает: хэш совпадает **или** `canJoinDifferentProfile()`
  вернул `true` — пропустить в `incomingRequests` (пользователь видит
  диалог); иначе — молча ответить `accepted: false` и не показывать
  ничего. Пользователю нечего одобрять в запросе, который в принципе
  не может привести ни к чему полезному.
- `canJoinDifferentProfile` — новый инжектируемый колбэк
  (`canJoinDifferentProfileProvider`, тот же паттерн, что уже был у
  `joinProfileForPairingProvider`). `AudilocApp` передаёт
  `() async => _awaitingProfileAdoption` — единственное легитимное
  исключение: устройство, явно нажавшее "Это моё второе
  устройство"/"Ждать сопряжения" (сценарий A, ADR 0013), и поэтому
  ожидающее подключения именно к чужому (для него) хэшу. Как только
  один раз произошло подключение, флаг снимается, и дальше это
  устройство — обычный участник с обычным профилем, для которого
  действует общий запрет.
- `approve()` не изменился по сути: раз запрос вообще дошёл до него,
  значит уже известно, что либо профиль совпадает, либо join разрешён.

### "Поделиться" — новый, независимый от профиля протокол

`lib/services/sync/share/` (`ShareServer`/`ShareClient`/`ShareService`)
— по образцу `services/sync/pairing/*`, но принципиально проще и не
трогает `devices`/CRDT-синк вообще:

- Работает с **любым** видимым по mDNS устройством
  (`nearbyPeersProvider`), сопряжено оно или нет, — файл-транспорт
  (`FileTransferServer`, `GET /tracks/<id>`) и так уже не проверяет,
  сопряжено ли устройство, так что скачивание работает без изменений.
- Офер несёт только превью (id/название/исполнитель/альбом) — не
  авторитетные данные. Принятие (`acceptOffer`) скачивает сам файл
  через `FileTransferClient.download(...)` и отдаёт
  **уже существующему** `LibraryImportService.importFiles(...)` —
  тот сам посчитает хэш-id по содержимому, вытащит теги из
  скачанного файла, скопирует в `synced_music/`, задедупит. Ноль
  нового кода для вставки в БД — то же самое, что делает обычный
  импорт папки, просто источник файла другой.
- Отдельный фиксированный порт `sharePort = 8544` — тот же принцип,
  что у `pairingPort`/`metadataSyncPort`/`fileTransferPort`: у каждого
  протокола свой порт, `DiscoveredPeer.port` для него не используется
  (как и `pairingPort` уже не использует его).
- Диалог принятия (`lib/features/shell/widgets/share_offer_dialog.dart`)
  показывает не только название, но и обложку — по запросу
  пользователя: должно быть видно, *что именно* предлагают, а не
  голый id. Обложка подгружается заранее, до решения
  принять/отклонить, через тот же `GET /covers/<id>` у отправителя
  (`FileTransferClient.downloadCover`, тоже без проверки сопряжения) —
  сам аудиофайл при этом ещё не скачивается, это происходит только
  при нажатии "Принять".

### Меню действий: трек

`LibraryScreen`'s `onLongPress` раньше вызывал
`confirmAndDeleteTrack` напрямую. Теперь — `showTrackActionsSheet`:
Редактировать (название/исполнитель/альбом/жанр — все поля уже были
у `Track`, `жанр` просто был неудалён из данных при ADR 0014, только
из UI; плюс обложка — по желанию заменяется картинкой из файла через
уже подключённый `file_picker`), Добавить в плейлист (новый
`add_to_playlist_sheet.dart`, использует уже существующий
`PlaylistsRepository.addTrack`), Поделиться (`share_track_sheet.dart`
— список устройств поблизости + переключатель "весь альбом"), Удалить
(без изменений, `confirmAndDeleteTrack`). Редактирование/Поделиться
недоступны, пока файла нет на этом устройстве
(`Track.isAvailableLocally`) — `TracksRepository.upsert` требует
локальный путь, а поделиться нечем, если файла ещё нет.

### Меню действий: плейлист + обложка

`PlaylistsRepository.rename()`/`.delete()` уже существовали — не
хватало UI. Добавлен `showPlaylistActionsSheet` (только для
пользовательских плейлистов, не для "Избранное"/"Удалённые"):
Переименовать, Удалить, Выбрать обложку.

Обложка — новое поле `Playlist.coverTrackId` (схема БД версии 3 → 4,
`ALTER TABLE playlists ADD COLUMN cover_track_id TEXT`) + новая таблица
`playlist_locations` (по образцу `track_locations`/ADR 0012 —
`playlistId:nodeId`, только для случая "картинка из файла"). Источник
обложки — ровно один из двух:
- **Обложка одного из треков плейлиста** — просто ссылка на id трека
  (`cover_track_id`), реальный путь резолвится через уже существующий
  `track_locations`. Синхронизируется бесплатно — это плейн-колонка со
  ссылкой, а не путь.
- **Картинка из файла** — кэшируется в `playlist_locations`, per-device,
  тем же способом, что и кастомный путь обложки трека.

**Осознанное сокращение объёма**: межустройственная синхронизация
самого файла картинки для случая "из файла" **не реализована** в этом
заходе — обложка, выбранная как файл, видна только на устройстве, где
её выбрали (`playlist_locations` — по-настоящему per-device таблица;
ничего не скачивает её на других устройствах того же профиля).
Обложка "из трека" синхронизируется полностью и сразу, т.к. использует
уже существующую инфраструктуру треков. Полноценный синк картинки из
файла потребовал бы отдельного sync-воркера по образцу
`CoverSyncService` и нового маршрута в `FileTransferServer` — решено,
что для декоративной фичи это непропорционально в рамках этого захода;
при необходимости — отдельная небольшая задача.

### Правый клик на десктопе

И `TrackTile`, и пользовательские `_PlaylistTile` в `playlists_screen.dart`
теперь реагируют на `GestureDetector.onSecondaryTap` тем же обработчиком,
что и `onLongPress` — на Linux/Windows нет жеста долгого нажатия, это
единственный способ дотянуться до меню действий там.

## Про журнал событий для синхронизации (не реализовано)

Отдельно поднятый вопрос: не стоит ли завести журнал событий из-за
растущего числа действий. Не сделано — `sql_crdt` уже хранит на каждой
таблице `hlc`/`node_id`/`modified`, это и есть HLC-упорядоченный журнал
изменений, поверх которого `crdt_sync` шлёт инкрементальные дельты, а
не полные дампы; собственный журнал для синхронизации был бы избыточен.
Если реально нужен read-only обзор истории для человека — это отдельная,
гораздо более узкая задача (экран, читающий уже существующие строки по
`modified`), не архитектурное изменение самого синка.

## Последствия

- Сопряжение больше не может привести к тому, что чужая библиотека
  окажется на устройстве без явного, специально запрошенного действия
  (кнопка "Ждать сопряжения").
- "Поделиться" не требует пары и не пишет ничего в `devices` —
  полностью отдельный, гораздо более узкий по последствиям канал.
- `test/unit/services/pairing_test.dart` — новые кейсы: запрос с
  несовпадающим хэшем без `canJoinDifferentProfile` никогда не
  доходит до `incomingRequests` (и получает `accepted: false`
  автоматически); с `canJoinDifferentProfile: true` — доходит, как и
  раньше. `test/unit/services/share_test.dart` — новый файл, реальный
  HTTP-раунд-трип offer/response + `acceptOffer`, по-настоящему
  скачивающий файл через `FileTransferServer` и импортирующий его
  через `LibraryImportService`. `test/unit/data/playlists_repository_test.dart`
  — новые кейсы на `setCoverFromTrack`/`setCoverFromFile`.
