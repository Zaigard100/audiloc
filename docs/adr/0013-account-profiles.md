# 0013. Аккаунты — отдельная локальная БД на профиль

## Контекст

Запрошенный сценарий: одним устройством пользуются несколько человек, у
каждого своя библиотека и свой набор сопряжённых устройств. До этого
ADR приложение предполагало ровно одну CRDT-идентичность (`nodeId`) и
одну БД на установку — то есть ровно одного "пользователя" на
физическое устройство.

## Решение

Каждый профиль — это **отдельная локальная БД и своя CRDT node id**
(`profiles/<id>/audiloc.db`), а не общая БД со столбцом `account_id`.
Причина: `TracksRepository`/`PlaylistsRepository`/`FavoritesRepository`/
`DevicesRepository` и весь `services/sync/*` (discovery, metadata sync,
pairing, file/cover transfer) не меняются вообще — профиль просто
открывает другой файл БД, и список сопряжённых устройств + вся
синхронизация становятся отдельными для каждого профиля бесплатно.
Обратная сторона: активен один профиль за раз, переключение — это
буквально выйти/войти заново. Это соответствует описанному сценарию
(по очереди, не одновременно несколько человек).

### Устройство

- `lib/data/profiles/profiles_store.dart` — **не CRDT**, простой
  локальный реестр (`<appSupportDir>/profiles.json`): список профилей
  + какой активен. `resolveActiveProfileId()` вызывается один раз при
  старте и всегда возвращает определённый id — пикер профилей поэтому
  никогда не обязателен на старте: помнит последний активный; если
  реестра ещё нет, но существует старая плоская `audiloc.db` (версии
  до аккаунтов) — переносит её (и `covers/`/`synced_music/`) в
  `profiles/<id>/`, не теряя ни библиотеку, ни сопряжения; иначе тихо
  создаёт один профиль — соло-пользователь не видит экрана аккаунтов
  вообще.
- `lib/core/profile_session.dart` — то, что раньше было телом
  `main()`, теперь параметризовано профилем: открывает БД, поднимает
  `ProviderContainer` с нужными overrides, стартует discovery/metadata
  sync/pairing/file+cover sync.
- `AudilocApp` (`lib/app.dart`) стала stateful-корнем — владеет
  сессией текущего профиля и умеет её пересобрать при переключении.
  Плеер и `AudioService.init` (Android) создаются один раз на процесс
  и переживают переключения — это железный/UI-слой, не данные профиля.

### Подводный камень: фиксированные порты

`metadataSyncPort`/`fileTransferPort`/`pairingPort` — общие константы
для любого профиля (снаружи через mDNS всё равно виден только текущий
активный). Значит при переключении **старая сессия обязана
по-настоящему освободить порты до того, как новая попробует на них
забиндиться**. `ProviderContainer.dispose()` этого не гарантирует —
Riverpod вызывает `ref.onDispose`-колбэки, не дожидаясь их `Future`.
`ProfileSessionHandle.close()` поэтому не полагается на
`container.dispose()` для сетевых сервисов: они останавливаются
`await`-ом, по одному, в явном порядке, и только потом
`container.dispose()`/`database.close()`.

Тот же принцип пришлось применить и на **старте**: `openProfileSession`
изначально был скопирован из `main.dart` с `unawaited(syncOrchestrator.start(...))`
— оставленным фоном ради того, чтобы не блокировать первый кадр UI.
Но это означало, что `openProfileSession` мог вернуться раньше, чем
`HttpServer` реально забиндился — и если сессию тут же закрывали
(именно так ведёт себя быстрое переключение профиля), `close()`
пытался остановить сервер, которого фактически ещё не было. Решение:
`metadataSyncService.startServer()` (сам биндинг порта) вызывается и
`await`-ится напрямую, отдельно от `SyncOrchestrator.start()` (который
всё ещё вызывает его же — идемпотентно, просто no-op) — а mDNS-часть
(`discoveryService.startAdvertising`/`startDiscovery`) остаётся
нествованной и вдобавок обёрнута в `try/catch` внутри самого
`SyncOrchestrator.start()`: сбой в bonsoir/платформенном плагине не
должен блокировать открытие библиотеки (ТЗ п.7 — синк бонус, не
шлагбаум).

Аналогично: фоновая работа при старте сессии (репэйр локальных
файлов/обложек, запуск `FileSyncService`/`CoverSyncService`) тоже не
`await`-ится в `openProfileSession` — но её `Future` сохраняется в
`ProfileSessionHandle._backgroundWork`, и `close()` теперь ждёт именно
её перед тем, как начать разбирать сервисы. Без этого `close()` мог
разобрать `CoverSyncService`, пока фоновая работа как раз собиралась
вызвать его `.start()` — новая подписка успевала создаться уже после
"закрытия", и первый же запрос к уже закрытой БД падал с
`DatabaseException`.

### Живая проверка: создание профиля висело в бесконечной загрузке

Реальный отчёт: создание нового профиля вешало UI на спиннере навсегда.
Причина — самая рискованная строка во всём этом ADR: `MetadataSyncService.dispose()`
(вызывается из `close()` при переключении) ждал `client.disconnect()`
для каждого подключённого пира по очереди, а `disconnect()` сам ждёт,
пока `crdt_sync` завершит close-хэндшейк по WebSocket — если реальный,
активно синкающийся пир не спешит его подтверждать (или просто
недоступен в этот момент), ожидание может не завершиться вовсе. Пока
`dispose()` ждёт, до строчки `_server?.close(force: true)` дело не
доходит — то есть порт вдобавок и не освобождается.

Исправлено на двух уровнях:
1. `MetadataSyncService.dispose()` — отключение всех клиентов теперь
   идёт параллельно (`Future.wait`) и с таймаутом 2с на каждого; после
   этого `_server?.close(force: true)` вызывается безусловно, что бы
   ни случилось с клиентами.
2. `ProfileSessionHandle.close()` — каждый шаг обёрнут таймаутом 3с
   как подстраховка на будущее: зависший шаг где угодно не должен
   вешать UI навсегда, даже если это не разъединение клиента.

### Первый запуск: имя профиля вместо тихого "Профиль 1"

По просьбе пользователя: на **совсем свежей** установке (нет ни
реестра профилей, ни старой `audiloc.db` для переноса) вместо тихого
создания профиля с именем по умолчанию показывается
`InitialProfileNameScreen` — простой экран с полем ввода. Отдельный
метод `ProfilesStore.needsInitialSetup()` фиксирует именно этот
случай, отдельно от `resolveActiveProfileId()`, у которого сценарий
переноса/восстановления активного профиля остаётся полностью тихим
(апгрейд с версии до аккаунтов не должен ничего спрашивать —
библиотека просто должна оказаться на месте). Создание *дополнительных*
профилей через `ProfileSwitcherSheet` уже спрашивало имя и не
менялось.

### Один и тот же человек, два своих устройства (сценарий A)

Уточнение от пользователя после первой реализации: описанный сценарий
на самом деле два разных. Уже сделанное выше — сценарий B ("несколько
людей на одном компьютере" — каждый получает свой изолированный
профиль). Есть и сценарий A: один человек, два своих устройства
(например, телефон + ноутбук) — они должны восприниматься как **один
и тот же профиль**, а не как два формально разных профиля, которые
просто синкают контент друг с другом.

Физическое ограничение никуда не делось: у каждого устройства
по-прежнему обязана быть своя локальная БД и свой CRDT `nodeId` — два
работающих процесса на разных машинах не могут буквально делить один
файл/один `nodeId` в архитектуре локальный-first P2P. Что реально
сделано вместо этого — два устройства одного профиля выглядят
одинаково для пользователя за счёт **общего имени**, переданного через
уже существующий канал сопряжения:

- **Инвариант "имя устройства = имя профиля".** `openProfileSession()`
  после `ensureSelfDevice()` сверяет `selfDevice.name` с `profile.name`
  и, если они разошлись, вызывает `identity.rename(profile.name)` —
  подтягивается при каждом открытии сессии, даже если профиль
  переименовали, пока это устройство не было активным.
- **`applyActiveProfileRename()`** (`lib/core/profile_session.dart`) —
  общая функция, которая переименовывает одновременно запись в
  `ProfilesStore`, self-device в `DeviceIdentityService` и живое
  состояние `currentProfileProvider` (теперь `StateProvider`, а не
  простой `Provider` — иначе UI не обновился бы без пересоздания
  сессии). Используется в двух местах: ручное переименование в
  `ProfileSwitcherSheet._renameDialog` (только если переименовывается
  именно активный профиль — у неактивного своя БД сейчас не открыта,
  имя подтянется само при следующем входе через инвариант выше) и
  автоматическое "принятие" имени ниже.
- **Кнопка "Это моё второе устройство — ждать сопряжения"**
  (`InitialProfileNameScreen`) — для первого запуска на втором
  устройстве того же человека: вместо ввода имени создаётся
  профиль-заглушка `"Новое устройство"`, сессия открывается как
  обычно, и `AudilocApp._watchForProfileAdoption()` слушает
  `knownDevicesProvider` этой сессии. Как только список сопряжённых
  устройств перестаёт быть пустым (обычный флоу подтверждения из
  [ADR 0011](0011-mutual-pairing-confirmation.md) — здесь ничего не
  меняется, ни `PairingService`, ни диалог подтверждения), берётся имя
  первого пира и `applyActiveProfileRename()` "перекрашивает" эту
  сессию в то же имя. Пока ожидание идёт, `MaterialApp.router`'s
  `builder:` рисует тонкий баннер сверху с ссылкой на вкладку
  "Устройства" — само приложение (библиотека, плеер) при этом
  полностью рабочее, ничем не блокировано.

Итог: с точки зрения пользователя оба устройства называются
одинаково и выглядят как один профиль, хотя технически это
по-прежнему два независимых `nodeId`, синхронизирующих одну и ту же
библиотеку через уже существующий CRDT-канал — архитектурно это то же
самое, что было и до этого уточнения, просто имя больше не расходится.

## Последствия

- Ноль изменений в уже отлаженных репозиториях/CRDT-слое.
- `SyncOrchestrator.start()` стал устойчивее к сбоям mDNS вообще, не
  только ради тестов — реальное улучшение для нестабильной сети.
- `test/unit/core/profile_session_test.dart` — реальный (не
  замоканный) тест, который открывает сессию, закрывает её и сразу
  открывает вторую **на тех же портах**; без описанных выше фиксов он
  падал с "Address already in use" — то есть тест поймал настоящую
  гонку, а не гипотетическую.
- `delete()` в `ProfilesStore` не трогает файлы профиля на диске —
  осторожный default, отмены для "удалил не тот профиль" иначе бы не
  было.
