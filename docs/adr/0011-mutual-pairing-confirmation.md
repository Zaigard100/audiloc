# 0011. Подтверждение сопряжения устройств с обеих сторон

## Контекст

До этого ADR сопряжения как отдельного шага не существовало.
`SyncOrchestrator` на любой `PeerFound` от `DiscoveryService` (mDNS)
безусловно добавлял пира в `devices` и сразу открывал синк;
`MetadataSyncService`'s серверная сторона точно так же принимала любое
входящее `crdt_sync`-подключение без проверки. Любые два AudiLoc на
одной LAN автоматически и молча сливали библиотеки — без единого
подтверждения с чьей-либо стороны.

Это вскрылось при разборе сценария "одним устройством пользуются
несколько человек, у каждого свой набор устройств" — стало ясно, что
без подтверждения сопряжения такой сценарий в принципе невозможен: чужое
устройство в той же Wi-Fi сети автоматически становится доверенным.

## Решение

`devices` — та же таблица, без изменений схемы, но с ужесточённым
смыслом: строка означает не "когда-либо увиденный по mDNS", а
"подтверждённо сопряжённый". Существующие строки (реальные сопряжения
из предыдущей живой проверки на двух устройствах) продолжают работать
без переподтверждения — миграция не нужна.

Новый модуль `lib/services/sync/pairing/`:

- `PairingServer`/`PairingClient` — простой HTTP-протокол (по образцу
  `FileTransferServer`, `anyIPv4`, порт 8543): `POST /pair/request`,
  `POST /pair/response`. Оба — fire-and-forget (202 Accepted), решение
  пользователя приходит асинхронно вторым запросом; транзакционность
  не гарантируется намеренно — потеря ответа при сетевом сбое просто
  означает, что инициатор попробует снова.
- `PairingService` — склеивает сервер/клиент с `DevicesRepository` и
  `MetadataSyncService`: `requestPairing`, `approve`, `reject`.
  `approve()`/принятый `response` пишут в `devices` и открывают синк
  только после подтверждения.
- `SyncOrchestrator` больше не апсертит и не коннектится на `PeerFound`
  автоматически — только если пир уже есть в `devices` (уже
  сопряжён). Обнаруженные, но не сопряжённые пиры видны в UI отдельно
  ("Найдено рядом", `unpairedNearbyPeersProvider`) с кнопкой
  "Добавить".
- `MetadataSyncService`'s серверная сторона (`_authorizeOrReject`)
  теперь тоже проверяет `peerId` против `DevicesRepository` и закрывает
  соединение до отправки ченджсета, если пира там нет — закрывает дыру
  и со входящей стороны, не только с исходящей. Иначе сопряжение имело
  бы смысл только для того, кто первым набирает номер.
- `DeviceTile` получил кнопку "Отвязать" (`Icons.link_off`) —
  `DevicesRepository.delete()` уже существовал, но не имел
  вызывающего UI.

## Последствия

- Больше никакого автоматического доверия — каждое сопряжение требует
  явного действия на принимающей стороне.
- Отвязка полностью обратима в другую сторону: устройство, снова
  увиденное по mDNS после отвязки, требует нового подтверждения.
- Протокол сопряжения — обычный HTTP без шифрования/аутентификации
  запроса как такового (см. те же оговорки, что в
  [ADR 0010](0010-built-in-file-transfer.md) про передачу файлов) —
  достаточно для доверенной домашней LAN, не рассчитано на враждебную
  сеть.
- Не тестируется юнит-тестом изменение в `SyncOrchestrator` напрямую —
  `DiscoveryService` не абстрагирован интерфейсом (обёртка над
  `bonsoir`), тестировать эту часть логики in-process негде; тот же
  предел тестируемости, что был у `SyncOrchestrator` и раньше.
  `PairingServer`/`PairingClient`/`PairingService` и серверная гейтинг-
  проверка в `MetadataSyncService` покрыты реальными (не замоканными)
  HTTP/WebSocket round-trip тестами.
- Задел под будущие аккаунты/профили (см. `docs/roadmap.md`): раз
  сопряжение живёт в той же `devices`, которая станет частью
  БД-на-профиль, список сопряжённых устройств у каждого профиля
  окажется отдельным бесплатно, без дополнительной работы.
