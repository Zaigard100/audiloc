# 0006. Id устройства = CRDT node id, без асимметричной криптографии

## Контекст

ТЗ п.6.3 описывает QR-код для добавления устройства "используя
публичный ключ как ID", что подразумевает настоящую пару ключей
(подпись/проверка). Полноценная схема (генерация keypair, подпись
handshake, проверка подлинности узла) — заметный объём
дополнительной работы и выходит за рамки того, что реально
используется дальше по конвейеру: ни `crdt_sync`, ни `bonsoir` не
требуют асимметричной аутентификации на этом MVP-этапе.

## Решение

Использовать сам `SqliteCrdt.nodeId` как публичный идентификатор
устройства:

- `sql_crdt` уже генерирует случайный node id и делает его стабильным
  за счёт того, что он "вшит" в HLC каждой записанной строки —
  переоткрытие БД восстанавливает тот же id из истории.
- `DeviceIdentityService.ensureSelfDevice()`
  (lib/services/sync/device_identity_service.dart) при первом запуске
  сразу пишет строку в `devices` — это не просто бухгалтерия: именно
  эта первая запись "фиксирует" node id в файле БД, иначе он бы
  генерировался заново при каждом холодном старте до первой записи.
- QR-код на экране "Устройства" кодирует именно этот id.

## Последствия

- Это identifier, не credential: он ничего не подписывает и не
  доказывает, что узел — тот, за кого себя выдаёт. Кто угодно в LAN,
  знающий/подсмотревший id, может представиться этим устройством.
  Приемлемо для MVP в доверенной домашней сети; для публичного
  релиза нужна отдельная итерация с настоящей парой ключей
  (например, через `package:cryptography`) поверх этого же
  MVP-фундамента — см. docs/roadmap.md.
- Название поля осознанно не называется "публичный ключ" в коде и UI
  (`Device.id`, "id устройства"), чтобы не создавать ложное
  впечатление о гарантиях безопасности, которых пока нет.
